# How to use and maintain the Atlas

## Use the catalog

- Search by project, organization, description, tag, license, language, or category.
- Filter by category, license, language, status, and favorites.
- Sort by stars, name, year, category, or latest reported push.
- Switch among grid, table, analytics, and comparison views.
- Export the filtered results as CSV or JSON.

The URL records most active view and filter choices, so a copied URL may reproduce them. A URL can therefore contain search terms, category choices, and comparison selections; review it before sharing.

## Understand repository metrics

On startup, the site loads its bundled catalog and then merges the scheduled `live-snapshot.json` (generated, stored on the `live-data` branch and pulled into `public/` at build time by `scripts/live-data.mjs`) baseline. Browser-cached metrics win when they have a newer `fetchedAt` timestamp.

Use **Sync GitHub** to request newer metrics for up to 60 tools in the current filtered set. Opening a tool detail can request that repository individually. Requests go from the browser to GitHub. Without a token, GitHub's unauthenticated limit is low; a partial refresh is normal when that limit is reached.

### Optional GitHub token

The key button accepts a token for higher GitHub API limits. Current behavior is:

- the token is stored in this site's browser `sessionStorage` (any older `localStorage` copy is deleted);
- it is discarded when the tab closes, or earlier if removed in the UI;
- it is sent as a bearer token only to `https://api.github.com/repos/...` by the application;
- it is not written into exports or the scheduled snapshot.

Use a fine-grained token restricted to public repositories and grant no unnecessary permissions. Do not use a broadly privileged token on a shared or untrusted device. See [PRIVACY.md](PRIVACY.md).

For local development, `VITE_GITHUB_TOKEN` is read only in development mode. Keep it in the gitignored `.env` file. The scheduled refresh instead reads `GITHUB_TOKEN` from the workflow environment and does not put that secret in the generated JSON.

## Add or correct a catalog entry

Before editing, read [docs/METHODOLOGY.md](docs/METHODOLOGY.md) and [docs/DATA_SCHEMA.md](docs/DATA_SCHEMA.md).

1. Search the catalog and open issues to avoid duplicates.
2. Verify the project's official site, public source repository, license, organization, and category.
3. Edit the relevant entry in `src/data/catalog.json`.
4. Keep descriptions factual and neutral; do not copy promotional claims without attribution.
5. Treat `hot` and non-`active` statuses as editorial decisions and explain the evidence in the pull request.
6. Run:

   ```bash
   npm run check-duplicates
   npm run lint
   npm run build
   ```

   Optionally, with `TYPESAFE_API_KEY` set, run a semantic check for near-duplicate projects, a mismatched category, and an implausible license or status claim:

   ```bash
   TYPESAFE_API_KEY=<key> npm run review:tool -- <new-tool-id>
   ```

   `check-duplicates` only catches exact id/name/repo collisions; this catches a rename, fork, or rebrand of an existing entry, and flags claims the entry's own description doesn't support. It's advisory without the key and never blocks `npm run validate`.

7. Open a pull request using the template and link supporting sources.

Do not hand-edit `live-snapshot.json` (generated, stored on the `live-data` branch and pulled into `public/` at build time by `scripts/live-data.mjs`) merely to update stars. Its metrics are generated by `scripts/fetch-stars.mjs` through the scheduled or manual workflow.

## The daily pipeline

`.github/workflows/discover-tools.yml` ("Daily catalog pipeline") runs at 11:20
UTC and on manual dispatch. GitHub may start scheduled runs late. In order:

1. **Pull the live state** from the `live-data` branch.
2. **Re-check every repository** (`scripts/fetch-stars.mjs`): stars, forks,
   issues and push times; renamed repositories are moved to their current name;
   entries that resolve to one repository are merged; archived or long-missing
   repositories are marked archived. A run that wants to remove more than 10
   entries this way changes nothing.
3. **Remove stale tools** (`scripts/prune-stale.mjs`, up to 25 per run): entries
   with `status: "archived"`, and repositories with no push in 18 months.
   Foundation models are exempt from the inactivity rule. Tools without live data
   are kept, and a snapshot older than 3 days is refused. Removed repos are not
   added to `src/data/excluded.json`, so a revived project can come back.
4. **Discover new tools** (`scripts/discover-tools.mjs`): see below.
5. **Verify** (`scripts/verify-catalog.mjs`) against live GitHub. Duplicate
   repositories, entries that could not be checked, and new entries that are dead
   or archived stop the run before anything is published.
6. **Publish** (`scripts/open-bot-pr.sh`): open a pull request, enable auto-merge
   and wait until it has merged. A failed required check leaves `main` untouched.
7. **Confirm** the live site was built from the new catalog
   (`scripts/check-live.mjs`).

Any failed step, a failed re-check, or a day below the minimum opens or updates a
"Daily catalog pipeline needs attention" issue. The run summary shows how many
tools were added and the verification report.

### Bot token

The daily pipeline and the hourly refresh first test the `KIMI_GITHUB_API`
secret (a personal access token) against the GitHub API, before checkout.

- **Token accepted:** it is used for everything. Its pushes, pull requests and
  merges trigger CI and the Pages deploy as usual.
- **Token missing, expired or revoked:** the run continues on the built-in
  `GITHUB_TOKEN`. Events made with that token start no workflows, so
  `scripts/open-bot-pr.sh` starts `ci.yml` on the bot branch itself (its checks
  land on the PR's head commit, which is what branch protection requires) and,
  after the merge, `deploy-pages.yml`. A rejected token opens or updates a
  "Bot token KIMI_GITHUB_API is expired or invalid" issue.

Renew the token before it expires and update the repository secret; the
fallback keeps publishing, with lower GitHub API limits.

### Discovery rules

A run aims to add at least 30 tools (up to 45). Every catalog category has its
own GitHub topics (`CATEGORY_TOPICS` in `scripts/discover-lib.mjs`; add an entry
when you add a category). The review queue takes one candidate per category in
turn, thinnest category first and stars descending within each, with at most 2
additions per category. While a run is short of the minimum it widens the search
(`SEARCH_TIERS`: older creation or push dates, lower star floors, deeper pages),
and as a last step raises the per-category limit for candidates that already
passed. A run reviews at most 400 candidates and
stays within a 45-minute budget. The minimum is a target:
**no check is relaxed to reach it**, and a shortfall is reported.

Every field is copied from the repository's own GitHub metadata. Nothing is
generated. Before a candidate is added it must:

- pass a deterministic relevance gate (`classifyRepo`) showing an AI/ML signal and
  not looking like reading material or curation;
- have a description and an identifiable license, and not be archived or a fork;
- pass a live TypeSafe semantic-duplicate check against the existing catalog;
- clear a 0.6 confidence bar on a live TypeSafe category classification;
- pass a stars-per-day plausibility filter.

Rejections are remembered in `audits/discover-rejects.json` and retried later (14
days for low category confidence, 30 for duplicates and name collisions). If
`TYPESAFE_API_KEY` is unset, nothing is added.

### Hourly refresh

`.github/workflows/refresh-stars.yml` runs step 2 every hour, publishes the
snapshot to `live-data`, proposes any resulting catalog correction through the
same pull-request gate, and redeploys the site.

### Checking by hand

```bash
node scripts/live-data.mjs pull
node scripts/prune-stale.mjs                              # read-only preview
GITHUB_TOKEN=<token> npm run verify:catalog               # read-only live check
```

## Automated semantic audit

`.github/workflows/typesafe-audit.yml` runs weekly (and on manual dispatch) and
reviews a rotating batch of the catalog (default 50 tools) with the TypeSafe
check from the section above, tracking coverage in `audits/state.json` so the
whole catalog rotates through roughly quarterly. Findings are posted to a
single, continuously-updated tracking issue rather than opening a new one each
run. It requires the `TYPESAFE_API_KEY` repo secret and skips cleanly without it.

## Review and update cadence

- **Automated baseline:** hourly, plus manual workflow runs when needed. The catalog pipeline runs daily.
- **Automated health check:** weekly validation and live link check (`catalog-health.yml`).
- **Catalog review:** pull requests and correction reports are reviewed as maintainer capacity permits; there is no guaranteed response time.
- **Editorial audit target:** maintainers should sample stale descriptions, links, licenses, statuses, and “Hot” labels at least quarterly. This is a governance target, not an automated guarantee.
- **Urgent trust issues:** security reports follow [SECURITY.md](SECURITY.md); privacy concerns should be clearly labeled and may be reported privately when they expose sensitive information.

## Remove or deprecate an entry

Moved repositories are followed automatically. Prefer setting an appropriate status over silently deleting history. Removal may be appropriate for duplicates, projects that no longer meet inclusion criteria, unverifiable entries, or material legal/safety concerns. Explain the reason and preserve review context in the issue or pull request.
