# Data Schema

The canonical catalog is the JSON data in `src/data/catalog.json` (re-exported with types by `src/data/tools.ts`); interfaces are defined in `src/types/index.ts`. This document describes the current contract but does not replace compiler and validation checks.

## `AITool`

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | string | Stable, unique, lowercase kebab-case identifier |
| `name` | string | Project's preferred public name |
| `org` | string | Responsible organization or maintainer label supported by a source |
| `cat` | string | One defined primary category `id` |
| `tagline` | string | Short neutral summary |
| `desc` | string | Factual overview of purpose and differentiators |
| `license` | string | SPDX-style identifier or accurate project-provided label |
| `lang` | string | Primary implementation language as cataloged |
| `stars` | number | Curated fallback/initial value; not guaranteed current |
| `repo` | string (optional) | GitHub `owner/name` coordinate (not a URL) used for refreshes |
| `tags` | string[] | Non-empty; search and secondary-capability terms |
| `hot` | boolean (optional) | Manual editorial discovery label; never imply it is computed |
| `status` | `active \| maintenance \| archived` | Limited status signal defined in the methodology |
| `year` | number | Project origin/public-release year when verifiable |
| `url`, `website`, `homepage` | URL string (optional) | Accepted by validation as absolute http(s) URLs; not currently rendered |

IDs should not be recycled after renames. Correct repository coordinates rather than creating a duplicate record for a move. Text must not contain secrets or unnecessary personal data. `scripts/catalog.mjs` (`validateCatalog`, run by `npm run check-duplicates`) enforces these rules and rejects any repo listed in `src/data/excluded.json`.

## `Category`

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | string | Stable kebab-case key referenced by tools and URLs |
| `label` | string | Display name |
| `icon` | string | Lucide icon key (mapped in `src/components/CategoryNav.tsx`) |
| `color` | string | Six-digit hex accent color |
| `blurb` | string | Scope of the category; also used as the TypeSafe category criteria |

Category totals and tool totals are derived from these arrays at runtime. Do not copy a numeric total into documentation unless it is generated from this source.

## Public read-only API

`scripts/generate-api.mjs` runs on every `npm run build` and writes the validated
catalog as plain JSON into `public/api/v1/`, which `vite build` then copies into
`dist/` alongside the site — so it's served from wherever the site itself is
hosted, with no separate backend:

| Path | Contents |
| --- | --- |
| `/api/v1/tools.json` | The full `AITool[]` array, same shape as this document's `AITool` table |
| `/api/v1/categories.json` | The full `Category[]` array |
| `/api/v1/meta.json` | `{ generatedAt, schemaVersion, toolCount, categoryCount, snapshotDate }` |

This is a free, unauthenticated, static mirror of the catalog — there is no
rate limiting or access control, because there is no server to enforce it. It
updates only when the site is rebuilt and redeployed, not live. A metered or
paid tier would need an actual backend (e.g. a small Worker in front of the
same data) rather than a static file.

## Scheduled snapshot

`live-snapshot.json` is generated by `scripts/fetch-stars.mjs`, not an editorial source file. It is stored on the `live-data` branch and copied into `public/` at build time by `scripts/live-data.mjs`. Its shape is:

```json
{
  "generatedAt": "ISO-8601 timestamp",
  "repos": {
    "<tool id>": {
      "stars": 0,
      "forks": 0,
      "openIssues": 0,
      "pushedAt": "ISO-8601 timestamp",
      "fetchedAt": 0,
      "history": [{ "t": 0, "s": 0 }]
    }
  }
}
```

`fetchedAt` and each history `t` are Unix milliseconds; `s` is the star count at `t`. History holds at most one sample per UTC day and is capped at 52 points (`src/lib/historyCore.js`, shared by CI and the browser). `validateSnapshot` in `scripts/catalog.mjs` checks this shape.

A tool may be absent when it has no repo, a request fails, or GitHub limits access; a failed repo keeps its previous entry. Consumers must tolerate absent/invalid snapshots and missing entries. The generated file contains public metadata, not the workflow token.

## Browser live data

The browser keeps the same per-tool `LiveRepoData` shape (`src/types/index.ts`) in `localStorage`, keyed by tool id. It merges the scheduled snapshot with records from **Sync GitHub** or a single-tool refresh; the record with the newer `fetchedAt` wins, and the longer history is kept.

Live data never changes a tool's catalog `status` in the browser. Only the scheduled refresh changes status: when GitHub reports a repository as archived, or returns a 404, `fetch-stars.mjs` sets `status: "archived"` in `catalog.json` and proposes it through an auto-merging pull request gated by CI. The UI separately shows a "Stale?" badge for an `active` tool whose last successful push observation is over a year old.

## Validation expectations

Run:

```bash
npm run check-duplicates
npm run lint
npm run build
```

Review should also verify unique IDs and repositories, defined categories, valid URLs, authoritative licenses, realistic years, non-negative numeric values, neutral descriptions, and evidence for editorial fields.
